# 服务盲区识别算法（Service Blind-spot Identification）

> 对应「15 分钟社区生活圈」配套标准：「系统能否准确识别出周边 1 公里内没有菜市场、药店或小学的『服务盲区』点位」。

本模块代码位于 `js/gap.js`（`GapFinder`），在看板、地图、体检报告中三处消费其结果。

---

## 1. 问题定义与判定口径

- **判定对象**：15 分钟步行等时圈（真实路网多边形）内部的所有居民点位。
- **盲区定义**：某一待判定点，到 **菜市场 / 药店 / 小学** 三类的**步行距离全部 > 1 km** → 该点即服务盲区点位。
  - 取三类里「最容易到达的那一类」的步行距离（记为 `worst`）作为该点的「缺口强度」：`worst > 1000m` 即判定为盲区（因为最小都超了，三类必然全超）。
  - 重度盲区：`worst > 1500m`。
- **为什么用步行距离而非直线距离**：生活圈语境下的「周边 1 公里」指**步行可达 1 公里**。直线距离会系统性高估可达性——绕行、过街天桥、封闭小区、断头路都会拉长实际路程，导致本该是盲区的点被误判为「有配套」。因此本算法以「直线距离 × 路网绕行系数 λ」外推步行距离。

---

## 2. 算法五步

```
等时圈多边形 ──①栅格采样──▶ 分析栅格点集合
                              │
        POI(菜市场/药店/小学) ─┤ ②λ标定（抽锚点调真实 WalkingRoute）
                              │
                   ③距离场插值（直线×λ 外推全域步行距离）
                              │
                   ④盲区判定（三类步行距离全>1km）
                              │
                   ⑤连通斑块聚合（4邻域连通分量 → Top-N 斑块）
```

### ① 栅格采样
在等时圈多边形的 bounding box 内按 `gridStepMeters`（默认 120 m）打正交栅格，用射线法（`pointInPolygon`）只保留多边形内部的点。
- **点数守卫**：预估点数 > 6000 时自动放大步长（最多 ×1.5³），防止超大等时圈卡死浏览器。

### ② λ 标定（路网绕行系数）
λ = 真实步行距离 / 直线距离。代表「这段路网平均要绕多远」。
- **锚点选取（关键）**：判定边界在「直线距离 ≈ 1000 / λ_default ≈ 800 m」附近，λ 在边界附近的准确性对最终判定影响最大。故先按 `|d_straight − target|` 升序圈出候选池，再用**最远点采样（FPS）**从池里挑出空间上尽量分散的 N 个锚点（默认 6 个），兼顾「贴近判定边界」与「覆盖不同方位」。
- **并发**：对锚点并发调用百度 `WalkingRoute`（默认 3 并发，复用 `Util.pmap` 限流）。
- **聚合**：取各锚点 λ 的**中位数**（抗异常值，个别锚点绕远路 λ 飙到 3+ 不影响）。
- **钳制**：`λ ∈ [1.00, 1.80]`，超出则钳到边界（路网绕行不可能 <1，>1.8 已是极端绕行，无继续放大意义）。
- **兜底**：样本 < 2 条（网络异常 / 路网无解）→ 退回经验值 `λ=1.25`，并在结果中标记 `lambdaFallback=true`，报告端提示「本项为估算值」。

### ③ 距离场插值（空间插值，零额外 API）
对每个栅格点，先求其到各类 POI 的**直线最近距离**（带空间索引加速，见 §3），再 `步行距离 = 直线距离 × λ`。
- 这正是「API 深度调用与工程优化」所鼓励的**空间插值**路径：用少量真实路网观测（λ）外推全域，而不是对每个栅格点都发一次路径规划请求（O(栅格×POI) 次）。

### ④ 盲区判定
`worst[i] = min(三类步行距离)`，若 `worst[i] > radiusMeters` → 盲区点；按 `worst[i]` 分「一般 / 重度」两级。同时统计每类单独超阈值的栅格占比（`missingRate`，用于看清「到底缺哪一类」）。

### ⑤ 连通斑块聚合
对盲区点做**栅格 4 邻域连通分量**分析，把离散点聚成「连片盲区斑块」；单点噪声（< 3 格）直接丢弃。每个斑块计算质心、面积、平均/最大缺口强度，**严重度 = 面积 × 平均缺口强度**，按严重度降序取 Top-3，作为「优先改造斑块」在地图打标签 + 看板列表呈现。

## 3. 工程优化

| 优化点 | 做法 |
|---|---|
| **空间索引** | 对每类 POI 建网格哈希（`IDX_CELL_DEG≈440m`），最近邻查询用「环形扩散 + 剪枝」，避免 O(栅格×POI) 全量距离计算；POI 数 ≤ 40 时直接暴力（少一次 Map 开销）。 |
| **API 次数控制** | 全程只花 `calibAnchors`（默认 6）次 `WalkingRoute` 做 λ 标定，其余全部空间插值；相比「每栅格一次路径规划」省下 2~3 个数量级调用。 |
| **并发限流** | `Util.pmap(arr, fn, concurrency)` 统一 3 并发，避免触发百度 QPS 限制。 |
| **超时降级** | 单次 `WalkingRoute` 6s 超时即视为失败（该锚点不参与标定），不影响整体。 |
| **点数守卫** | 超大等时圈自动放大栅格步长，防止主线程长时间阻塞。 |
| **渲染性能** | 盲区点（动辄数百上千）用 **Canvas 覆盖层一次性绘制**（仿 heatmap.js），而非给每个点加 `BMapGL.Circle` 矢量对象；仅 Top-3 斑块用矢量 Label（数量极少无压力）。随地图平移/缩放实时重投影。 |
| **确定性** | 算法主体无随机性（FPS 锚点选取为确定性贪心），同输入两次运行结果完全一致，便于回归与答辩复现。 |

### 与 AK 类型限制的关系
本项目浏览器端 AK（见 config.local.js / CI Secret，源码仅保留占位符）调用百度 Web 服务（含 `routematrix/v1/walking` 批量距离矩阵）会返回 `status=240「APP 服务被禁用」`。因此「批量距离矩阵」路径走不通，本算法走项目交付要求明确给出的**等价路径**：并发请求（6 次 WalkingRoute 标定）+ 空间插值（距离场外推）。既满足「控制 API 调用次数」的工程优化要求，又规避了大批量路径规划。

## 4. 输入 / 输出契约

**输入**（`GapFinder.analyze(center, polygonPts, resultByKey, onProgress)`）
- `center`：体检中心点 `{lng, lat}`
- `polygonPts`：等时圈多边形顶点数组（来自 `Isochrone.build`）
- `resultByKey`：`POI.fetchAll` 的返回值，至少包含 `market / pharmacy / school` 三类的 `items`
- `onProgress(p, msg)`：进度回调

**输出**（核心字段）
- `enabled` / `ok`：是否成功
- `gridCount` / `gapCount` / `severeCount` / `gapRatio` / `gapAreaM2`
- `lambda` / `lambdaFallback` / `lambdaSamples` / `lambdaDetail`：λ 标定透明度
- `gapPoints[]`：盲区点位明细（lng/lat/三类距离/缺口强度/瓶颈类）
- `patches[]`：Top-N 连片斑块（质心/面积/严重度）
- `centerStatus`：中心点自身盲区状态（报告里最常被问到的一句话结论）
- `missingRate` / `bottleneckCount`：各类缺失率与卡脖子统计
- `_grid/_walk/_isGap/_level/_worst/_keys`：渲染 / 调试内部引用

## 5. 精度自检与已知边界

- **λ 透明度**：λ 值、样本数、是否兜底，全部随结果返回并在看板/报告展示，可复核。
- **方向性校验**（测试覆盖）：盲区质心应位于 POI 簇的反方向（配套集中在西侧 → 盲区集中在东侧），反方向成立说明算法未把「离 POI 近」误判成盲区。
- **已知边界**：
  1. λ 是**全局单一系数**，不随方位变化；在路网各向异性极强的区域（如被河流分割）会引入局部误差。已在重度阈值留 500m 缓冲 + 连通聚合降低单点噪声影响。
  2. `WalkingRoute` 失败率较高时 λ 退回经验值 1.25，此时盲区判定偏保守（可能多报一些盲区）。
  3. 判定严格依赖 POI 检索召回率；若某类 POI 被百度 LocalSearch 漏检，会虚高该类缺失率。
